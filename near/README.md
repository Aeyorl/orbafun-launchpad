# Orba on NEAR (testnet demo)

This workspace contains Orba's NEAR implementation: Rust contracts, a Rust API/indexer, and a Next.js interface. This is a testnet prototype, not an audited production launchpad.

## Workspace

- `contracts/token`: NEP-141 fungible token with NEP-148 metadata; launchpad holds curve and reserved inventory.
- `contracts/launchpad`: token creation, constant-product curve, milestone burns, treasury unlocks/claims, event emission. The token WASM is supplied to `new` and stored in launchpad state for token-account deployment.
- `backend`: Axum REST API, PostgreSQL schema, and finalized-block event indexer.
- `sandbox-tests`: NEAR Workspaces integration tests for sandbox. Runs on Linux/macOS; on Windows use WSL2.
- `scripts`: build/deploy helper scripts.
- `docs/DECISIONS.md`: explicit demo preset and fee allocation assumptions.
- [60-day supply simulation](docs/SIMULATION.md): compares the three milestone presets under four trading scenarios.
- `apps/web/src/app/near-demo`: minimal UI route.

## Prerequisites

Install Rust stable, `cargo-near`, NEAR CLI, Node/npm, and PostgreSQL. Official NEAR Rust quickstart: https://docs.near.org/smart-contracts/quickstart. The contract requires a NEAR testnet account with enough testnet NEAR to deploy the launchpad and fund token subaccount creation. The launchpad must also be storage-registered with the USDC contract.

```powershell
cargo install cargo-near --locked
rustup target add wasm32-unknown-unknown
Push-Location near
.\scripts\build-contracts.ps1
cargo test --workspace
Pop-Location
```

The build script expects to be run from the repository root and builds both contract artifacts. The token WASM is passed as the `token_wasm` argument when initializing the launchpad; it is not compiled into the launchpad binary. Do not put signing keys in source control.

## NEAR Sandbox integration tests

NEAR Workspaces sandbox tests are supported on Linux/macOS. From PowerShell, build the WASM artifacts with the Windows Rust target, then run the local chain tests under Ubuntu WSL2:

```powershell
wsl --status
Push-Location near
cargo build --release --target wasm32-unknown-unknown -p orba-near-token -p orba-near-launchpad
Pop-Location
wsl -e bash -lc 'cd "<repo-path>/near/sandbox-tests" && cargo test'
```

The sandbox suite covers token creation, invalid-token and slippage refunds, oversized-buy refunds at curve inventory exhaustion, failed token delivery recovery, buy/sell, one-shot milestone burns and event emission, failed treasury and fee payout recovery, fixed-recipient and creator/owner authorization, successful treasury, fee, and sale-proceeds claims, full reserved-supply burn, and post-graduation trading lock. Sandbox testing uses the NEP-141 token contract as a local test USDC faucet; this is not the live NEAR USDC contract.

## Testnet deployment

Initial testnet deployment is recorded in [`deployment.testnet.json`](deployment.testnet.json). The launchpad contract account is `launchpad.orba-near-demo-41c9.testnet`; its owner is `orba-near-demo-41c9.testnet`. Both account keys were generated by `near-cli-rs` and saved in the Windows keychain. Do not export or commit those keys.

The launchpad WASM is deployed and initialized, and the launchpad has been registered on Circle's NEAR testnet USDC contract for FT storage. Deployment and initialization were verified through finalized NEAR RPC reads. The local web app environment is stored in ignored `apps/web/.env.local` with the public contract IDs and API URL.

Deploy the existing build to another testnet account with the Rust CLI, then initialize it using `file-args` for the large token WASM payload. Use `near account create-account sponsor-by-faucet-service` for a new owner and `near account create-account fund-myself` for its launchpad subaccount. For this deployment, the launchpad init call required `250 Tgas` prepaid gas and used about `111 Tgas`.

## Backend

From PowerShell, start the isolated local PostgreSQL database and Rust API/indexer with:

```powershell
.\near\scripts\start-local-api.ps1
```

The script stores the database under the Ubuntu WSL user's local data directory, binds PostgreSQL to loopback port `55432`, and starts indexing from the latest finalized testnet block. It uses dRPC's NEAR testnet JSON-RPC endpoint because NEAR's legacy public `rpc.testnet.near.org` endpoint is deprecated and tightly rate-limited. The indexer checkpoints in batches of up to 50 blocks and only requests transaction status for relevant launchpad and NEP-141 transfer-call actions. Keep the PowerShell process open while using the API.

The web demo starts from `apps/web` with `npm run dev`; its script selects Webpack for compatibility with the existing Next.js configuration. Contract view calls use the same dRPC endpoint through `NEXT_PUBLIC_NEAR_RPC_URL`.

The API can also be started manually:

```powershell
$env:DATABASE_URL = 'postgres://...'
$env:NEAR_RPC_URL = 'https://near-testnet.drpc.org'
$env:LAUNCHPAD_ACCOUNT_ID = 'your-launchpad.testnet'
cargo run -p orba-near-api
```

Routes: `GET /health`, `/api/tokens`, `/api/tokens/:id`, `/api/tokens/:id/trades`, `/api/tokens/:id/mechanics`. The database migration runs at startup. Configure `NEXT_PUBLIC_NEAR_API_URL` for the Next.js demo. Indexing is idempotent by transaction/event key and finalized block checkpoint.

### Vercel + Neon hosting

Historical block scans use `NEAR_ARCHIVAL_RPC_URL` (defaults to NEAR's public testnet archival RPC). Public archival scans are limited to three blocks per invocation to reduce rate-limit failures. For sustained catch-up, configure a dedicated archival RPC and run the continuous worker. Current reads and transaction replay continue to use `NEAR_RPC_URL`. A missing historical height only advances the checkpoint if a later finalized block proves the chain skipped that height. Read the stored checkpoint at `GET /api/indexer/status`.

The Next.js project is configured to build the Rust Axum API as a Vercel Rust function (`apps/web/api/axum.rs`) and route `/api/*` requests through it. The Vercel Neon integration supplies the pooled `DATABASE_URL`; the Rust service applies the checked-in PostgreSQL migration on startup. Set `NEXT_PUBLIC_NEAR_API_URL` to the site's origin, plus `NEXT_PUBLIC_NEAR_RPC_URL`, `NEXT_PUBLIC_NEAR_LAUNCHPAD_ID`, and `NEXT_PUBLIC_NEAR_USDC_ID`. The server also needs `NEAR_RPC_URL`, `LAUNCHPAD_ACCOUNT_ID`, `NEAR_USDC_ACCOUNT_ID`, `INDEXER_START_BLOCK`, `INDEXER_BATCH_BLOCKS`, and a randomly generated `CRON_SECRET`.

Vercel's Hobby cron runs at most once per day, so the UI asks the Rust indexer for a bounded sync immediately after a wallet transaction; a database advisory lock and 15-second cooldown limit concurrent/repeated work. The authenticated scheduled endpoint `/api/cron/indexer` provides a daily catch-up. Use a continuously running worker or a Vercel plan with more frequent schedules if near-real-time indexing outside user activity is needed.

## Demo flow

1. Open `/near-demo`, connect a NEAR testnet wallet, select a milestone preset, and create a token with a fixed treasury recipient.
2. Register the launchpad with USDC storage management, then approve/transfer-call USDC to buy along the curve.
3. Transfer-call created tokens to the launchpad's sell receiver to sell; the seller then claims accrued USDC proceeds.
4. Cross a configured cumulative volume threshold; the launchpad burns reserved supply and unlocks part of the per-token treasury pool.
5. Connect as the fixed recipient and claim an unlocked tranche.
6. Token creators can claim their accrued fee share with `claim_creator_fees`; the launchpad owner can claim protocol fees with `claim_protocol_fees`. Both amounts are restored if the USDC transfer fails.
7. Confirm trades and `EVENT_JSON` records in the backend API and NEAR testnet explorer.

The smallest preset's thresholds require real testnet USDC volume; for a repeatable milestone demo, use a sandbox or a separately documented test-only preset. Never present a local mocked milestone as a testnet transaction.

## Known scope limits

- Milestones count settled buy volume, not unique holders. Fees make repeated buys costly, but one trader or coordinated wallets can still push a milestone. The demo has no proof of unique identity.
- Each launch stores its preset and treasury recipient. The testnet contract account still has a deployment key that can replace the contract code, so these rules are not immutable against an upgrade.

This testnet implementation does not yet include AMM graduation, rich token metadata storage, production rate limits/auth, robust chain reorg recovery, or production financial controls. Sandbox coverage exercises the contracts; contract deployment and wallet transaction flows must be validated in the current environment before claiming end-to-end testnet completion. The contracts remain a testnet prototype and need security review, gas/storage budgeting, and independent audit before meaningful funds are used.
